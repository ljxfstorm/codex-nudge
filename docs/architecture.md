# 认证与恢复

工具拥有自己的私有目录，不读取 Codex、SIWC 或其他程序的凭据，也不调用它们的进程。每次认证操作由 `StateStore` 持有进程锁，覆盖读取、写入意图、网络请求和结果落盘，避免并发消费一次性授权码或 refresh token。存储使用原子替换和 fsync；HTTP 不自动重试或跟随重定向。

`identity.py` 用 PyJWT 及其 crypto 依赖验证 ID token 的签名、issuer、audience、有效期和初次登录的 nonce。密钥地址限于可信 issuer。使用成熟验签库，避免自行实现密码学；其余 HTTP、存储、CLI 使用标准库。access token 不作为身份声明来源，其中未验证的 exp 仅作到期提示。

`auth.py` 管理浏览器 PKCE 和凭据状态。授权链接可在另一台机器打开，完整 localhost 回调通过隐藏终端输入交回；工具不监听端口。授权只申请 openid、profile、email、offline_access。用户显式传入兼容 client ID；该路径的技术验证不代表官方公共接口承诺或注册许可。

登录在 `login.json` 中从 `waiting` 进入 `exchange_pending`，随后才发送一次授权码交换。成功保存经验证的新凭据后记录 `complete`，清除临时 verifier、state、nonce。拒绝授权记录 `denied`。中断或交换响应丢失时保留 `exchange_pending`，禁止重发，需重新授权；只有仍在等待回调的登录才能继续提交回调。

凭据在 `credentials.json` 中有三个阶段：

| 阶段 | 含义 | 可执行操作 |
| --- | --- | --- |
| `ready` | 已验证身份，并核对额度响应的账户 | 查询、显式续期或重新授权 |
| `refresh_pending` | 已记录续期意图，但没有完成保存新结果 | 重新授权；禁止重发续期，也不能用旧 access token 查询来解除 |
| `verification_pending` | 新结果已验证身份并保存，尚未确认额度账户 | 仅 GET 复核，无需再次交换或续期 |

续期先持久化 `refresh_pending`，再 POST 一次。新响应通过身份和账户绑定校验后，保存为 `verification_pending`，然后 GET 额度核对账户，成功才进入 `ready`。响应丢失、验签依赖的网络请求失败或落盘失败都可能留下不确定状态；即使实际上未消费 token，也不猜测或重发。重新授权必须保留同一 client、subject 和账户；切换账户需要单独目录。

`quota.py` 保留 bucket、时长和未知字段的语义，不把 weekly 或额外 bucket 当作缺失的 5h。额度耗尽不等于登录无效。查询成功也不证明窗口已经固定锚点。

## 最小请求与 5h 调度

`inference.py` 只实现固定配方和兼容请求头，不提供多模型路由。请求体使用 `store=false`，流式响应不跟随重定向、不自动重试。收集器限制总字节和单事件字节，逐块检查 45 秒预算，底层网络空闲超时 15 秒；该预算在块之间检查，不承诺整个连接过程的硬性墙钟上限。终止事件必须确认完成、模型一致且 usage 有效，正文与加密 reasoning 不落盘。兼容字段不是官方支持承诺，接入边界见[兼容性说明](compatibility.md)。

`schedule.py` 中的 `Schedule` 在内存中为单个普通 Codex 5h 窗口分类。已有使用量或稳定 reset 表示活跃窗口；过去的 reset 等待服务端刷新；100% 且 reset 随查询时间移动，需要两次样本才能进入 `ready`。已知活跃窗口尊重边界加宽限时间。查询时长进入时序判断，防止慢请求被误判为已启动窗口；墙钟明显回退则停止。

`PersistentSchedule` 在同一 module 内封装调度的保存与推理尝试恢复，使用 watch 已持有租约的 `StateStore`。它负责观测后保存、复核失败时保存阻断、发送前持久化 `sending`、响应校验失败时保存安全原因，以及完成结果落盘后返回摘要。`watch` 只使用 `observe`、`wake_once` 和 `delay`，不读取或修改尝试 phase，也不决定异常后的补写时机。磁盘仍使用 schema 1，无迁移要求。

`watch.py` 将状态机与认证、传输串联。整个 watcher 持有 `watch/` 子目录租约，凭据目录的锁只在实际操作时持有，因此休眠期间仍可登录或查询。调度记录与账号的 client、subject、account 哈希绑定。`--send` 明确授权必要续期和推理；默认观测不 POST。发送模式可对已持久保存的 `verification_pending` 凭据自动完成 GET 验证，包括一次续期成功后验证查询暂时失败的情况；`refresh_pending` 仍须重新授权，只读 watch 不自动改变认证阶段。

只有明确的普通额度 GET 与凭据验证 GET 进入 watcher 的重试循环。网络及 5xx 错误按 5、15、45 秒退避，最多额外 3 次；429 每次至少等待 300 秒。传输层仅提取有界 `Retry-After` 的有效秒数或带时区 HTTP 日期，不保留原文；非法值回退本地策略。GET 重试等待取服务端要求与本地退避的较大值；第四次失败若仍含服务端等待要求，则先以 `read_cooldown` 等待后退出，防止监督器立即开始新一轮查询。总请求预算不增加，等待只在当前进程保留。`--once` 失败即返回；预算耗尽后仍交给监督器。每次成功查询的起止时间单独测量，不把退避时间用于浮动 reset 判断。退避期间普通查询的 access token 到期时，发送模式返回显式续期阶段，只读模式停止；未验证的新凭据到期仍要求人工恢复。成功后重新观测，发送前预检继续使用新查询。预检错误不包裹整个 `wake_once` 重试；推理、授权码交换和 refresh POST 都不进入此循环。无效 JSON、超大响应和参数错误明确标记为不可重试，防止将协议错误当网络故障无限重启。

发送前 `AuthSession.wake_once` 持有凭据锁，重新 GET 额度，再调用 `PersistentSchedule` 提供的 `reserve` 回调。它重新核对浮动窗口、使用权限与样本新鲜度，原子保存 `sending` 后才允许一个 POST。这个回调仅承担“判定并持久化发送意图”的事务边界，不负责网络重试。另一客户端的并发请求仍有同秒竞争可能，最终查询能缩小但不能消除该竞争。

| 推理阶段 | 行为 |
| --- | --- |
| `sending` | 请求意图已经落盘，远端结果尚未可靠保存；重启停止，禁止补发 |
| `completed` | 收到并保存完成状态和 usage；只继续查询验证 |
| `verified` | 两次发送后样本固定在请求附近；等待下一窗口 |
| `blocked` | 响应校验失败，或 reset 漂移/不符合请求时间；停止自动发送 |

完成响应保存前发生中断或写入失败，磁盘仍是 `sending`。收到完成状态后无需为断点恢复重新推理，只查询约 +5 秒、+35 秒的 reset；重启太晚、无法证明原窗口时也停止。状态只保留最近一次请求，历史事件由标准输出的 JSON 行承载。当前不提供跳过不确定标记的选项。

响应状态/类型及流内容校验失败时，`InferenceError` 附带 HTTP 状态码和白名单媒体类型；参数及未知媒体类型内容不回显。`PersistentSchedule` 在已有 `sending` 意图时将这些安全字段保存为 `blocked` 的 failure，不保存任意错误正文或回复。缺失 usage 不等于零消耗；该记录只能说明接收失败，不能判断服务端是否已经完成推理。backend Lite 可能返回没有 Content-Type 头的有效 SSE，因此 HTTP 200 时允许该头缺失；显式提供的媒体类型仍必须为 text/event-stream。所有响应均须通过完整 SSE 终态、完成状态、模型、输出项和 usage 校验，JSON、HTML、仅有增量或 DONE 的流不算成功。产品不保存响应正文。

## 到期兑换与恢复

`resets.py` 只保留机会 ID、状态、精确到期时间及套餐支持，忽略推荐人、头像与文案。基于官方 Codex rust-v0.164.0 的固定实现（`6aaac694803004a63c6f393d153c96d22521a6b9`），通过 WHAM `rate-limit-reset-credits` GET 查询，POST 到其 `/consume` 路径，提交 `credit_id` 与 `redeem_request_id`。该请求不执行模型推理。只有发送模式且显式配置提前量时才消费，额度尚未耗尽不会在客户端阻止兑换；服务端决定适用窗口。

`ExpiringResets` 复用 watcher 的生命周期租约，将账户绑定与单个兑换尝试保存在私有 `watch/resets.json`。最终额度 GET、机会 GET、意图保存和 POST 在 `AuthSession` 凭据锁内完成；意图未保存就不 POST。`sending` 表示结果尚未保存，`received` 表示收到明确成功但尚未确认，`verified` 表示同一机会已标为 redeemed 且后置额度查询账户匹配，`skipped` 表示服务端明确返回 nothing_to_reset 或 no_credit。无效果结果冷却 300 秒后可基于新查询创建新尝试。

恢复先查原机会；已兑换则只做后置查询，仍可用时仅用原幂等键和原 ID 重试，最多四次 POST；服务端 Retry-After 进入持久 retry_at。过期后不再 POST，但仍可查询确认已有兑换。未知响应保留 sending 并停止；确认超过十分钟也停止。sending 状态下，计数变化或详情缺失不能证明已兑换；received 已保存明确成功结果，历史列表省略条目时可用该结果与后置额度查询完成确认。

推理正在复核时暂缓兑换。兑换待确认期间阻止推理，确认后由 `PersistentSchedule.after_reset` 清除旧窗口观测并保存，保留已验证的推理记录；下一轮重新分类真实额度。兑换本身的确认不要求观测到 100%，因为其他客户端可以同时使用额度。兑换凭据/机会标识与原始响应不进入日志和诊断。

## 配置与服务

`config.py` 读写显式指定的私有 JSON 文件。配置创建先写入随机 0600 临时文件并 fsync，再以硬链接原子发布，不覆盖任何已有文件或符号链接；发布后的目录同步失败也保留完整结果。读取拒绝非普通文件、其他用户所有的文件、公开权限、重复键、未知字段和版本。相对状态路径以配置文件目录为基准，不依赖启动 cwd，不插入 shell 或环境变量。配置不保存 token。

CLI 的参数优先级为命令行、配置、默认值。`setup` 只创建配置，不登录或启用服务；持久自动发送需显式 `--enable-send` 或用户编辑配置。`watch --no-send` 能覆盖配置中的自动发送；普通查询命令始终只读。`service` 只生成文件，由用户检查后交给 systemd。

`service.py` 保留 venv 解释器的原始绝对路径，不 resolve 到系统 Python。服务通过绝对源码路径导入开发态模块，不依赖 WorkingDirectory；`ExecStart` 的 `:` 前缀禁用 systemd 的 `$` 展开，`%` 仍双写转义，参数按 systemd 语法引号和反斜杠转义。解释器位置受 systemd 的额外字符限制，不能含引号或反斜杠。服务文件不嵌入凭据，也不通过 shell 启动。

CLI 的 watch 在主线程临时安装 SIGTERM 处理器，退出后恢复原处理器。收到信号以专用 `BaseException` 展开操作栈，释放凭据与 watcher 锁，尽力写入 `stopped_at` 和 `stop_reason=terminated`，并返回 0；清理期间重复 SIGTERM 不再次打断。信号不完成或清除发送/续期意图；已发送但尚未保存结果仍按不确定状态恢复。其他线程中的库调用不接管进程信号。

watch 的可重试传输错误返回 1，普通错误、认证/状态/协议错误及无法恢复的 HTTP 状态返回 2。服务仅延迟重启前者，遇到 2 停止。推理与续期结果不明即使引发一次进程重启，也会被持久状态阻止重新发送。原生验收既检查 unit 语法，也实际启动无账户的一次性模块核对字面参数；不以字符串断言替代 systemd 行为。

## 脱敏诊断

`diagnostics.py` 对本地记录逐字段投影，输出环境、配置开关、阶段和数值；身份、路径、凭据、任意字符串和原始记录不透传。`read_snapshot` 复用有界私有 JSON 读取，但不创建目录或锁文件，也不获取 watcher 的生命周期租约，因此后台运行时仍可诊断。写者原子替换保证单个记录完整，多文件之间不承诺同一事务时点。此接口只用于观测，认证和调度事务继续使用 `StateStore` 锁，诊断不会修改、续期或解除阻断。

watcher 在持有生命周期租约时覆盖写入 `watch/health.json`，保存版本、实际发送开关、启动/更新时间、最后成功 GET、下次动作、读重试计数和固定枚举错误分类。启动保留上次成功查询时间，重新设置本次运行阶段；损坏的健康快照可以重建，写入仍检查文件归属、权限和类型。可捕获退出清空下次动作并记录原因，健康记录写入失败不覆盖已有的原始异常。它不保存任意异常正文，不代替 `schedule.json` 的发送意图，也不参与是否允许推理的判定。

诊断在 `watcher.runtime` 中投影健康记录，版本格式、阶段、动作、时间、计数与错误状态码均单独验证。超过下次预定动作（或最后更新）60 秒才标记 `overdue`，正常长休眠不视为超时。该指标只是过时提示，不是进程探测；启动早期的 SIGTERM、落盘失败、掉电和强制终止没有最终落盘保证，进程存活与退出状态以监督器为准。健康记录固定覆盖，无额外心跳查询或无限增长的文件日志。
